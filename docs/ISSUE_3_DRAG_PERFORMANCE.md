# #3 区域与历史列拖动性能

本轮处理 v0.4.23 发布后反馈的“区域和列拖动卡顿”。修复已打入 v0.4.24 本地安装版及绿色版，并更新本机标准安装；尚未创建 GitHub Release。交付与验证见 [v0.4.24 本地更新](RELEASE_NOTES_v0.4.24.md)。

## 行为

- 左右区域、底部高度、历史列和底部三栏的鼠标移动按动画帧合并，只处理最新位置。松手时补齐最后坐标；取消拖动时完成已收到的位置更新并清理监听。
- 区域拖动仅更新对应网格的行或列，松手后保存原有布局偏好。历史列宽度只作用于历史区，避免让工作区的大量文件节点重复计算样式。
- 调整图谱列宽只重绘图谱，复用已有提交关系和行节点；设置页恢复默认布局时同步恢复图谱宽度。
- 继续支持原有最小尺寸、独立拉宽、历史横向滚动、键盘调整和底部三栏比例保存。Git 操作和独立文件编辑器的 MergeView 行为不变。

## 性能复现

使用临时 Git 仓库的约 3,000 条提交与 4,000 个改动文件，在真实 Chromium、1920×1080 视口下，连续 40 帧、每帧发送 8 次移动事件。测量经过实际拖动监听器，记录帧间隔、样式写入次数、尺寸读取次数和提交行重建次数。

| 场景 | 修复前帧间隔中位数 | 本地修复后中位数 |
| --- | ---: | ---: |
| 左侧栏 | 250 ms | 16.7 ms |
| 右侧栏 | 300 ms | 16.7 ms |
| 底部高度 | 283 ms | 16.7 ms |
| 提交信息列 | 33.4 ms | 16.7 ms |
| 图谱列 | 150 ms | 16.7 ms |
| 底部两处分隔条 | 33.4 ms | 16.7 ms |

旧代码中左右区域及底部高度每轮读取计算样式 642 次；修改后为 4 次。图谱列每轮重算提交关系和重建行各 40 次；修改后均为 0。上述数字是本机固定夹具的实测结果，不代表所有硬件和仓库都不会掉帧。

## 顶部列分隔线补修（2026-09-08）

用户在首轮本地更新后确认仍卡的是图谱、提交信息等顶部列分隔线。追加复现发现：原来只在提交超过 240 条时启用虚拟列表，默认 120 条和加载两页后的 240 条会渲染所有行，拖动时屏幕外的行也反复计算样式。首轮大历史夹具启用了虚拟列表，遗漏了普通列表的这条路径。

固定 120 条、四列各 40 帧的对照中，原逻辑样式计算累计约 9.56 秒，仅切换到可见范围渲染后降为 2.40 秒，恢复原逻辑又升到 10.72 秒。原逻辑每帧中位数约 67–100 ms；首次冷运行可达 167 ms。图谱关系和提交行重建计数均为 0，说明首轮优化仍有效，剩余耗时来自屏幕外行的样式计算。

补修复用现有虚拟列表：提交行总高度超过可见区域便启用，不再等到 241 条；可见区域及上下缓冲行正常绘制，滚动时补齐对应提交。没有减少加载的提交，也不改变 Git、列宽存储、图谱连线和行对齐。

- 新增普通 120／240 条真实历史夹具下四个列分隔线的高频拖动、原生鼠标输入、松手定位、屏幕外节点数量及滚动到底部检查。旧代码先触发 P95 83.4 ms 的失败；修复后专项通过，P95 不超过约 33.4 ms。
- 69 项定向测试通过。完整 Chromium 回归在项目发布工作流已有的性能倍率 3 下通过；第一次默认倍率运行在新检查之前触发原有冷 Git API 耗时门槛（385.2 ms），没有修改测试门槛。列拖动自身 P95 70 ms 门槛不受倍率影响。
- 使用实际安装后的 EXE、隔离设置和真实临时 Git 历史再次运行普通列表专项，通过；四列中位帧间隔约 12–24 ms，P95 最大约 30.4 ms，松手跳变 0 px。测试结束进程正常退出。
- v0.4.24 保持版本号，仅生成本地补修构建。最新安装包和绿色包位于 `dist/local-0.4.24-header-installer/` 与 `dist/local-0.4.24-header-portable/`；首轮本地产物保留。本机标准安装已替换，四份设置哈希未变，桌面和开始菜单仍指向标准安装。尚未发布 GitHub Release。
